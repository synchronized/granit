# Windows Clang Queue 提交基线

## 环境

- Granit：`f222bb8`
- 构建：Windows Clang 22.1.8、Release、共享库
- 系统：Windows AMD64
- CPU：Intel Core i5-8600K，6 个逻辑处理器
- 每线程每样本提交：100 个预录制的空 Recorder
- 重复：每个线程和 frames-in-flight 档位完整运行 3 次

每次运行包含 2 次预热和 10 个正式样本。Recorder 创建和 begin/end 发生在计时前；计时区间只
包含并发 `submit` 调用，pending 等待与 Recorder 销毁位于计时后。`ns/op` 和吞吐量按全部线程
墙钟时间计算，P50/P95/P99 则来自每次 `submit` 调用的延迟分布。

## 观察与边界

- 单线程下 1、2、4 个帧槽的吞吐差异不大，当前空命令负载没有证据表明增加到 4 个帧槽能稳定
  提高提交吞吐；1 帧槽的一次 P99 尖峰也说明短样本容易受调度或驱动噪声影响。
- 固定 2 个帧槽时，2 线程相对单线程总吞吐提高约 19%，4 线程仅再提高约 1%，符合单 graphics
  Queue 和内部 Queue 互斥最终串行化的预期。
- 并发线程主要影响尾部而非中位数：4 线程 P50 仍约 1.9～2.1 微秒，但 P95 上升至
  20.5～61.9 微秒，P99 达到约 201～209 微秒。P-03 应优先用 ETW/WPA 或 CPU profiler 区分
  Queue 互斥等待、Fence/帧槽复用和操作系统调度。
- 本用例提交空 Recorder，用于隔离 CPU 提交路径，不代表包含真实资源屏障和大量命令的帧耗时。
- Recorder 的 pending 清理和 GPU 完成等待不计入吞吐区间，但帧槽在 `submit` 内部发生的复用等待
  会被计入，这正是 P-02D 的测量目标。
