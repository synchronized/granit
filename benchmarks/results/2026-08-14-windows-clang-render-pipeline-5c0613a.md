# Render Pipeline 与 H-05 性能对比

## 结论

当前统一 Render Pipeline 的 CPU 性能已达到 H-07H 暂定目标。复用资源并为同步门面选择 Upload
内存后，方向光自动路径 CPU P50 由 2.907 ms 降至 0.799～0.800 ms，下降约 72.5%；同条件最小
回调为 0.614～0.638 ms。自动 Shadow/Opaque 的剩余 CPU 与 GPU 等待增量约 0.16～0.19 ms。

## 环境与方法

- 初始基准代码：基于提交 `5c0613a` 的工作区；优化复测基于提交 `0639c31` 后的工作区。
- 系统：Windows AMD64。
- 编译器：Clang 22.1.8。
- 构建：Release，共享库。
- 初始参数：5 个预热样本，20 个正式样本，每个样本 20 帧。
- 优化复测参数：10 个预热样本，50 个正式样本，每个样本 20 帧。
- 统一路径：64×64，一个三角形、一盏方向光、真实 1024×1024 Shadow Draw、PBR 与 Tone Mapping。
- 手工路径：256×256，一个全屏三角形、一盏方向光与一个点光、1×1 Shadow Clear、PBR 与
  Tone Mapping。
- CPU 区间均包含录制、提交、等待；不包含初始化和像素回读。
- H-05 GPU 时间来自 Vulkan timestamp query，不包含 CPU 录制和等待。

两条路径的输出链相同，但 Shadow 和分辨率并非严格等工作量。本结果用于发现门面开销风险，不能
作为 Shader 吞吐量的逐项等价比较。

## 判断与下一步

- 最小回调路径与手工 H-05 的 CPU P50 相差约 6%，说明 Graph、瞬态附件、Tone Mapping 和统一
  提交外壳不是 4 倍级差异的主要来源。
- 第一轮优化复用每个 Draw 的 Frame/Object Uniform Buffer、Bind Group 和 Shadow/IBL 光照资源，
  Uniform Buffer 使用可直接更新的 Upload 内存，并复用固定 1024×1024 阴影附件。
- 方向光自动路径 P50 下降约 1.537 ms，说明每帧创建和销毁绑定资源是主要可消除开销。
- 无灯光场景中，自动路径相对最小回调增加约 0.345 ms，可归因于 Opaque 资源更新、命令录制和
  GPU 完成等待。
- 方向光场景相对无灯光场景增加约 0.423 ms；扣除最小回调的约 0.013 ms Graph 增量后，方向光
  打包、Shadow 资源更新、真实 Shadow Draw 和对应 GPU 等待合计约 0.410 ms。
- Opaque 与方向光/Shadow 路径约各占剩余增量的 45.7% 和 54.3%，下一步分别增加 GPU timestamp，
  判断两部分主要受 CPU 更新/录制还是 GPU Draw/等待限制。
- Render Pipeline 每次提交后等待完成，因此其缓存常量和灯光 Buffer 可以安全使用 Upload 内存；
  通用 Lighting 资源仍默认使用 `automatic`，避免改变允许多帧在途的调用方语义。
- Upload 策略把方向光自动路径再次降低约 0.571 ms。两次 50 样本复测中自动路径稳定在
  0.799～0.800 ms，已经低于“最小回调 P50 的 1.5 倍加真实 Draw 成本”的暂定 CPU 目标。
- H-05 的 Shadow 仅清除 1×1 深度目标，而自动路径执行真实 1024×1024 Shadow Draw；下一轮应
  建立严格等工作量用例。
- 统一门面完整 GPU 时间需要内部测试专用测量钩子或外部 GPU profiler。不得为基准扩张公共 ABI。
- 下一步补充阶段级 GPU timestamp，确认优化没有以额外 GPU 等待换取 CPU 数字；未来允许多帧
  在途时，必须把当前原地更新改成按 Frame 生命周期管理的 Upload 环形分配。
- 优化目标先定为同条件 CPU P50 不高于最小回调路径 1.5 倍加真实 Draw/GPU 等待成本；若无法达到，
  应记录不可消除成本和原因。
