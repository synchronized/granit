# Windows Clang 持久化上传上下文复测

## 环境

- Granit：`c7f7b63`
- 构建：Windows Clang 22.1.8、Release、共享库
- 系统：Windows AMD64
- CPU：Intel Core i5-8600K，6 个逻辑处理器
- 每线程每样本上传：10 次
- 重复：每组参数完整运行 3 次

每次运行包含 2 次预热和 10 个正式样本。目标资源、CPU 数据和 Renderer 均在计时前创建。
本次实现为每个 Renderer 预建与 frames-in-flight 等量的上传上下文，并按需复用持久映射的
staging Buffer、Command Pool、Command Buffer 和 Fence。现有同步 API 仍在 GPU 完成后返回。

## 结论

- P-04A 达成目标：小型同步上传固定成本显著下降，1 MiB 路径也没有回归。
- 持久化对象和缩短 Queue 锁范围改善了多线程扩展；Texture 四线程仍有明显波动，单 Queue
  提交和同步 Fence 等待依然是上限。
- 当前每次同步写入仍产生一次 Queue submit 和一次 Fence wait。继续压缩逐帧小上传成本需要
  P-04B 的显式批量上传边界，不能通过悄悄改变现有同步 API 语义实现。
- 本次未加入公开性能计数器；对象创建次数可由实现结构确定：Renderer 初始化时每个上传槽创建
  一套提交对象，staging 仅在容量不足时增长。若后续需要长期回归监控，应增加仅用于基准构建的
  内部计数，而不是扩展公共 ABI。
