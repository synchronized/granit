# Windows Clang 延迟销毁队列基线

## 环境

- Granit：`2c12645`
- 构建：Windows Clang 22.1.8、Release
- 系统：Windows AMD64
- CPU：Intel Core i5-8600K，6 个逻辑处理器
- 线程：1 个独立 CPU benchmark 工作线程
- 重复：每个资源规模和批量档位完整运行 3 次

每次运行包含 2 次预热和 10 个正式样本。入队用例在计时前创建强引用，收集用例在计时前填充
队列；资源使用轻量 `uint64_t` 对象，不包含 Renderer 外层互斥、Registry 操作或 Vulkan 资源析构。

## 资源规模扩展

固定每个完成序号包含 100 个资源。`ns/op` 是三次运行平均值的均值；入队和收集的 op 为单个
资源，序号推进的 op 为一次 next、commit 和 mark-completed 周期。

| 用例 | 资源/序号数 | 平均 ns/op | 三次运行范围 ns/op |
| --- | ---: | ---: | ---: |
| 退役入队 | 100 | 406.567 | 323.700～563.600 |
| 退役入队 | 1,000 | 67.327 | 66.240～68.890 |
| 退役入队 | 10,000 | 60.097 | 58.638～62.422 |
| 序号推进 | 100 | 423.633 | 219.500～749.900 |
| 序号推进 | 1,000 | 31.813 | 29.560～33.740 |
| 序号推进 | 10,000 | 6.506 | 6.460～6.594 |
| 批量收集 | 100 | 327.667 | 313.800～348.900 |
| 批量收集 | 1,000 | 64.027 | 61.630～68.610 |
| 批量收集 | 10,000 | 45.284 | 40.824～49.166 |

## 观察与边界

- 100 条规模的结果由工作线程唤醒、join 和计时器固定成本主导，波动显著，不适合用于推断容器
  单操作价格；1,000 和 10,000 条结果更稳定。
- 每个资源使用独立完成序号时，`std::map` 批次节点成本明显；增加同完成点批量大小可同时降低
  入队和收集成本，说明实际帧内共享提交序号的退役模式有利于当前结构。
- 收集在每批 100 个资源后趋于稳定，继续增加到 1,000 没有可见收益；入队仍因更少的 map 查找
  与节点而改善。该结果不构成强制批量阈值，实际资源析构成本通常远高于轻量测试对象。
- 序号推进在足够大循环中约为 6.5 ns/cycle，目前不是优先优化候选。
- 本用例使用线程私有队列，未测量 `renderer_state::retirement_mutex_` 竞争；P-02B 已覆盖 Registry
  锁趋势，若实际帧路径仍指向退役锁竞争，应在 P-03 使用 profiler 验证后再设计并发基准。
