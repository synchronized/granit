# Canvas Draw List 与动态几何首份 CPU 性能基线

## 环境

- 日期：2026-08-14
- Granit：`056a0c8`
- 系统：Windows AMD64
- CPU：Intel Core i5-8600K 3.60 GHz
- 编译器：Clang 22.1.8
- 构建：Release、共享库
- 样本：20，预热：3，完整运行重复 3 次

## P50 范围

| 用例 | 100 矩形 | 1,000 矩形 | 10,000 矩形 |
| --- | ---: | ---: | ---: |
| Draw List 构建 | 4.734～4.866 µs | 104.577～116.251 µs | 1.303～1.386 ms |
| 全兼容合批扫描 | 0.278～0.290 µs | 2.535～2.570 µs | 26.400～27.400 µs |
| 全部交替状态扫描 | 0.187～0.195 µs | 2.053～2.071 µs | 33.760～49.160 µs |
| 复用 Buffer 的几何上传 | 0.489～0.505 µs | 3.128～3.514 µs | 31.390～39.280 µs |

Draw List 构建包含顶点、索引和 Item 容器增长以及局部索引修正。几何上传复用已经分配的 Upload
Vertex/Index Buffer，不包含首次创建或扩容。该表是 CPU 墙钟时间，不是 GPU timestamp。

## Draw 与绑定计数

| 输入 | Item | Batch | Indexed Draw | Texture/Sampler 更新 |
| --- | ---: | ---: | ---: | ---: |
| 相邻状态全部兼容 | N | 1 | 1 | 1 |
| Texture 与 Scissor 逐项交替 | N | N | N | N |

合批不会跨不相邻 Item 重排，因此交替状态是有意保留透明顺序的最坏情况。上层应尽量让相同
Texture、Sampler、Scissor 和 Layer 的内容相邻，但不能为减少 Draw 破坏透明顺序。

## 基线发现与判断

- 首轮 10,000 矩形构建 P50 约 35.5 ms。基准定位到每次追加都精确 `reserve` 索引容量，导致
  O(N²) 重分配；改为 `vector` 摊销增长后降至 1.303～1.386 ms，约降低 96%。
- 合批扫描和已分配 Buffer 上传在 10,000 矩形时均低于 50 µs，目前没有依据引入并行扫描、
  无锁容器、永久映射或额外暂存复制。
- 10,000 矩形 Draw List 构建已超过 1 ms。H-06C 后续应先评估调用方容量预留和批量追加接口，
  再考虑线程化；当前内部接口仍未进入公共 ABI。
- 本基线未测量 UI Pass GPU timestamp。GPU 成本会强烈受到实际 Batch 数、覆盖像素、混合和纹理
  采样影响，应在 H-06D 接入参考管线后以兼容与交替两组状态分别测量。

## 复测条件

- 顶点布局、索引宽度、容器增长、合批键或上传内存策略改变。
- 增加容量预留、批量追加、Bind Group 缓存或多线程构建。
- 同环境 P50/P95 相对本基线稳定退化超过 10%。
- H-06D 完成 Tone Mapping 后 UI 合成并建立 GPU timestamp 基线。
