# Windows Clang 批量 Queue 提交结果

## 环境与参数

- Granit：`e7cce95`
- 构建：Windows Clang 22.1.8、Release、共享库
- 系统：Windows AMD64
- CPU：Intel Core i5-8600K，6 个逻辑处理器
- 每线程每样本 Recorder：100
- frames-in-flight：2
- 每组运行：5 次预热、30 个正式样本
- 重复：1 线程和 4 线程各完整运行 3 次

`queue_submit` 逐个调用单 Recorder 提交；`queue_submit_batch` 对同组 100 个 Recorder 调用一次
批量 API。`ns/op` 和吞吐量按 Recorder 数归一化。逐个提交的 P50/P95/P99 是单次 API 调用
延迟；批量提交的分位数是整批调用耗时除以 Recorder 数，因此只适合比较单位 Recorder 的摊销
和长尾，不表示批量调用本身只耗时该数值。

## 对比与结论

- 4 线程批量提交相对同版逐个提交，平均 `ns/op` 降低约 24.7%，平均吞吐提升约 31.9%。
- 4 线程单位 Recorder 的归一化 P99 从 155～169 微秒降到约 8.7～13.4 微秒，说明减少 Queue
  锁获取、Fence 复用和 Vulkan 提交次数有效收敛了多线程长尾。
- 1 线程批量提交平均吞吐相对同版逐个提交提升约 41.7%，但两组都出现过系统调度离群样本，
  因此不能只引用单轮最好值。
- P-02 的单提交 1 线程平均值为 5,155.367 ns/op；本次为 5,406.656 ns/op，约增加 4.9%，仍在
  预定 5%～10% 波动门槛内。P50 从约 1.8～1.9 微秒降至 1.0 微秒，没有稳定的快速路径退化。
- 批量路径不是循环调用单提交：它原子校验全部句柄，使用一次 `vkQueueSubmit2`，整批共享一个
  帧槽、Fence 和 submission serial，同时为每个 Recorder 保留按序的布局转换 preamble。

本结果只覆盖空 Recorder 的 CPU 提交固定成本。实际帧仍应按资源依赖组织合理批次，不能为了
追求批量大小而跨越本应独立处理的错误边界或交换链帧边界。
