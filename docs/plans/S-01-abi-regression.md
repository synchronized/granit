# S-01：C ABI 回归验证

## 状态

- 设计状态：已确认
- 实现状态：已完成
- 路线图任务：S-01
- 优先级：P1
- 前置依赖：核心 Renderer 公共 C API

项目仍处于开发阶段，本计划建立的是变更检测能力，不代表开始承诺 API 或 ABI 稳定。发生有意的
破坏性修改时，可以同步更新基线，但必须让差异在代码审查中清晰可见。

## 背景与目标

现有 C11 头文件编译测试和 C/C++ 行为测试可以发现声明与链接错误，但不能完整覆盖以下问题：

- 函数已经写入公共头文件，却没有真实导出到共享库。
- 描述结构字段顺序、对齐或大小被无意改变。
- 枚举、标志位、句柄大小或无效值等 ABI 常量发生漂移。
- 共享构建和静态构建使用了错误的导出宏配置。

S-01 为这些边界建立自动回归，保证未来开始兼容承诺时已有可靠基础。

## 非目标

- 当前不冻结函数集合、结构布局或枚举值。
- 当前不建立 Vulkan 原生互操作 ABI。
- 安装后外部 Consumer 和包版本兼容由 S-03 负责。
- 不检查 C++ 包装的二进制 ABI；`.hpp` 层以源码兼容和 C ABI 转发为主。

## 已确认决策

- 共享库测试不链接 `granit`，而是在运行时独立加载产物并逐项查找公共 C 符号。
- 导出基线覆盖 `GRANIT_API` 声明的核心 Renderer C API；新增或删除接口时显式更新测试清单。
- 静态构建不运行动态加载测试，继续通过真实链接、C11 头文件和 C++20 包装测试验证。
- ABI 基线只记录跨边界可观察事实，不记录编译器私有类型或 Vulkan 实现细节。

## 实施顺序

1. S-01A（已完成）：共享构建独立加载 Granit，并检查全部公共 C 导出符号。
2. S-01B（已完成）：为核心句柄、结果码、关键常量、资源、Pipeline、Recorder、Attachment、
   Surface、Swapchain 和查询结构建立 C11 数字基线。
3. S-01C（已完成）：验证资源描述的最小尺寸、未知尾部兼容，以及 Graphics Pipeline V1～V5
   只读取对应版本字段的行为。
4. S-01D（已完成）：Linux CI 覆盖 Clang/GCC × 共享/静态四组合；安装后的 C11、C++20、
   核心和 RenderPipeline Consumer 会验证目标类型、静态宏传播并实际运行。
5. S-01E（已完成）：为 Granit 0.1.0 核心 C ABI 建立带 component、平台、架构和编译器
   身份的正式快照；CI 继续通过导出符号和 C11 数字基线比较 ABI 漂移。

## 测试与验收

- 共享库缺少任一公共 C 符号时，`granit.abi.exports` 必须失败并报告符号名。
- 公共结构字段顺序、大小、对齐或关键常量变化时，C11 编译测试必须失败。
- Windows 与 Linux 共享构建使用同一份符号基线。
- 静态库构建不依赖动态加载 API，现有 C/C++ Consumer 继续通过。
- 文档明确区分“能够检测变化”和“承诺不发生变化”。

首份快照位于 `tests/abi/snapshots/0.1.0`。它是变更检测基线，不改变当前 0.x 兼容承诺。

## 风险与未决问题

- 结构布局基线必须按字段偏移表达，不能只比较总大小，否则字段重排可能漏检。
- 32 位平台加入支持后需要独立确认指针字段布局；当前基线以受支持的 64 位平台为准。
- `granit_render_pipeline` 是独立 component，其公共导出将在核心 S-01 验证稳定后单独纳入。
