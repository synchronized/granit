# S-81：0.44.0 独立纹理变体上传

## 状态

- 文档状态：已确认范围
- 实施状态：已完成
- 目标版本：v0.44.0
- 需求来源：Gneiss `UPSTREAM-044` 的 U44-01

## 背景与目标

`granit_upload_batch_write_texture_asset_mips` 当前把 Payload 指针解释为整个 Manifest
Payload 的起点。Manifest 中位于非零 `variant.payload_offset` 的变体因此不能直接使用独立
读取的局部缓冲，迫使上层保留或重建未选择的前缀。

本计划新增一个明确的变体局部负载入口：调用方传入所选变体起点和完整变体长度，Granit
继续负责 Manifest 校验、变体摘要校验、Mip 范围检查、Upload Batch 预算和提交生命周期。

## 非目标

- 不把 Gneiss 的 VFS、Manifest 来源、资源预算、任务调度或 RID 生命周期下沉到 Granit；
- 不实现视距驱动 Mip 流送、虚拟纹理、纹理 LOD 或通用内存管理器；
- 不改变现有完整 Payload 基址入口的语义；
- 不支持只提供部分 Mip 的局部负载，除非另立摘要粒度和所有权设计；
- 不新增后端专用或 Vulkan 类型公共接口。

## 已确认决策

- 新入口使用与现有入口相近的 C ABI 和 C++ 包装，名称明确表达“所选变体负载”；
- 局部 Payload 的 `data_offset` 从零开始解释，`variant.payload_offset` 不再加到调用方指针；
- 仍验证完整变体长度、完整变体 SHA-256、Mip/数组层范围和目标 Texture 描述；
- 成功入队后复制或接管所需数据，调用方可立即释放原始局部缓冲；
- 前置校验失败不得添加 Upload Batch 操作，预算不足返回既有 `NOT_READY` 语义；
- 旧入口保留原始完整 Payload 基址语义，避免静默改变已有调用方。

## 实施顺序

1. 在 Asset Format 层抽取可复用的“完整变体局部 Payload 校验”逻辑，覆盖溢出和摘要边界；
2. 新增 C API、C++ 包装和文档入口，保持旧 API 行为不变；
3. 在 Upload Batch 实现中复用现有 Mip 编排、预算、失败清理和资源生命周期；
4. 增加首个变体、非零偏移变体、RGBA8 回退和多变体顺序的 CPU/C API 回归；
5. 增加真实 GPU 上传与回读，覆盖取消、销毁、释放调用方缓冲和旧 API 回归；
6. 在 Vulkan 与 WebGPU 支持路径上运行相关测试，完成安装 Consumer、文档和跨平台验收。

## 测试与验收

- 独立缓冲上传首个和后续变体，结果与完整 Payload 入口一致；
- 覆盖错误索引、错误长度、损坏摘要、截断、整数溢出、错误 Mip 范围和目标纹理不匹配；
- 覆盖预算不足、重试成功、前置失败后 Batch 为空、取消和销毁；
- 覆盖无 BC7 设备选择 RGBA8 非零偏移变体，不以缺少 BC7 跳过验收；
- 新增接口不泄漏 Vulkan 类型，不改变旧 ABI 符号和旧入口行为；
- Windows、Linux、Emscripten、共享/静态安装 Consumer 与文档链接检查通过。

## 风险与未决问题

- C ABI 函数命名和是否复用现有描述结构需要在实现 PR 中固定，并同步 ABI/安装快照；
- 当前 Upload Batch 是否已复制完整变体数据，需要以源码和测试确认，不能只依据文档推断；
- Gneiss 的预算统计、来源读取、设备代次和重试仍由 Gneiss 负责，不作为本计划验收项。
