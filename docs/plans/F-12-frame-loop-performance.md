# F-12：帧循环性能诊断与提交优化

## 状态

- 设计状态：已确认
- 实现状态：未开始
- 路线图任务：F-12
- 优先级：P1
- 前置依赖：F-04、F-06、F-09、F-10、F-11、S-08

## 背景与目标

F-10 消除了实时窗口每帧立即重置单个 Recorder 的串行等待，F-11 又将完整 ImGui Demo 的
Canvas Record 从约 0.104 ms 降至约 0.040 ms，并显著降低多纹理批次的 GPU 时间。然而示例的
整体 FPS 增幅有限，说明 Canvas 录制已不一定是全帧主导成本。当前显示的 FPS 也无法区分事件处理、
ImGui 构建、Draw Data 转换、Swapchain acquire、帧槽等待、命令录制、Queue submit、present、
Validation 和驱动调度。

本任务先建立可重复、可机器读取的全帧基线，分离 CPU 工作、CPU/驱动等待和 GPU 执行时间，再只
优化被证明确认的可控热点。目标是降低代表性实时窗口路径的帧时间和尾延迟，同时守住正确性、输入
延迟和跨平台行为，而不是追求脱离显示模式与工作负载的单一峰值 FPS。

## 非目标

- 不预设 Canvas、Queue、Swapchain 或 Validation 必然是下一瓶颈。
- 不用关闭 Validation、跳过等待或放宽同步规则掩盖正确性问题。
- 不通过无限增加 frames-in-flight 换取吞吐；帧槽数必须同时评估输入延迟。
- 不承诺在 FIFO、桌面合成器或驱动限速下达到固定 FPS。
- 不在缺少证据时引入 Bindless、Render Graph、异步计算或新的公共 C ABI。
- 不将 Vulkan Queue、Fence、Semaphore、Timestamp 或原生句柄暴露给普通用户。
- 不把仅在单台开发机出现的驱动差异写成 Granit 的通用行为。

## 已确认决策

### 全帧时间线是唯一归因入口

同一测量窗口至少记录以下互斥或可明确解释的阶段：

1. 事件处理与应用更新；
2. ImGui 新帧、Demo 构建和 Draw Data 生成；
3. ImGui Draw Data 到 Canvas 的转换；
4. Swapchain acquire 及其内部帧槽等待；
5. Canvas 与其他命令录制；
6. Recorder end、Queue submit 和提交侧等待；
7. present 调用及其 CPU 等待；
8. GPU 时间戳覆盖的渲染区间；
9. 无法归入上述阶段的剩余全帧时间。

CPU wall time 与 GPU timestamp 不得相加为“总帧时间”，因为两者可能重叠。等待指标必须标明调用点
和语义，不能只记录一个无法定位的 `wait_ms`。

### 使用分布而不是单次 FPS

每组配置先预热，再使用固定时长或固定帧数采样。报告样本数、p50、p95、p99、最大值和 FPS；平均
值仅作辅助。测量记录必须包含构建类型、编译器、Validation、窗口尺寸、Present Mode、帧槽数、
Demo 开关、纹理负载、GPU、驱动和显示环境。

示例标题栏可以保留平滑后的可读 FPS，但验收数据必须来自原始样本，不能使用标题刷新周期或整数
取整后的显示值。

### 固定实验矩阵后再比较

首轮矩阵至少覆盖：

| 维度 | 配置 |
|---|---|
| 构建 | Release；必要时补 Debug 诊断，不跨构建直接比较 |
| Validation | 关闭、开启 |
| Present Mode | Immediate、FIFO；不支持时明确记录 |
| 帧槽 | 1、2、3、4 |
| UI 负载 | 字体/状态窗口、完整 ImGui Demo、Demo 加自定义纹理 |
| 窗口 | 固定尺寸与 DPI，前台且不调整大小 |

跨配置比较使用同一机器、同一电源模式和相近后台负载。FIFO 结果用于验证帧节奏和正确性；解除显示
限速的配置才用于观察引擎吞吐上限。

### 优化由证据闸门控制

F-12A/B 完成前不改动提交或同步架构。后续阶段只有在目标成本满足以下条件时进入实现：

- 在稳定采样中可重复，并能与计时点或 profiler 调用栈对应；
- 在代表性配置的 p50 或 p95 中占有足以影响总帧时间的比例；
- 属于 Granit 可控范围，而不是显示器限速、桌面合成器或应用主动等待；
- 有不破坏同步、资源生命周期和输入延迟的最小改动方案。

若没有单项满足条件，本任务以诊断结论收尾，不为了产生代码改动而优化。

### 帧槽吞吐与输入延迟共同验收

1～4 个帧槽的对比必须同时记录槽位等待、全帧分布和估算排队深度。默认值只在跨平台结果证明
吞吐收益稳定且交互延迟可接受时调整；否则保留当前默认值，并把更高槽数作为调用方显式选择。

## 实施顺序

1. **F-12A 可重复基线**：为 SDL3 + ImGui 示例或独立 benchmark 增加低扰动阶段计时、预热、固定
   采样窗口和 CSV/JSON 输出；定义固定场景与运行参数。
2. **F-12B 热点归因**：执行完整矩阵，并结合 CPU profiler、GPU timestamp 和等待调用点，区分
   应用 CPU、Recorder、Registry/锁、资源保留、驱动提交、acquire、present 与 GPU 成本。
3. **F-12C Recorder/提交优化**：仅在 F-12B 证明成立时，缩短资源查询与保留路径、合并重复状态
   校验或减少 Queue 提交固定成本；不得缓存跨 reset 后失效的裸内部指针。
4. **F-12D Swapchain 调度优化**：仅在 acquire/present 或帧槽复用被确认是可控热点时，调整等待
   位置、批次或默认调度；保持 OUT_OF_DATE、Surface Lost、取消帧和退出排空语义。
5. **F-12E Validation 成本解释**：定位 Validation 开启时的额外调用和同步检查，修复 Granit
   产生的冗余工作；Validation 自身不可消除的固定成本单独报告。
6. **F-12F 收尾验证**：复跑 Windows/Linux、共享/静态和代表性 Present Mode，更新性能 Record、
   示例说明与路线图；实现结果和原始数据不持续追加到本计划正文。

## 测试与验收

- 计时开启与关闭时渲染输出、事件处理、资源生命周期及 Validation 结果一致。
- 采样器不在热路径逐帧格式化或写磁盘，输出失败不会破坏帧循环。
- CPU 阶段可解释全帧 wall time，剩余项被显式报告；GPU 时间与 CPU 时间保持不同时间域。
- 覆盖 1～4 个真实帧槽、Validation 开关、Immediate/FIFO 和三种 UI 负载。
- 每个结论至少基于预热后的稳定样本，并报告 p50、p95、p99，而非只报告最佳 FPS。
- 若进入优化阶段，目标热点在代表性解除限速配置下的 p50 与 p95 至少下降 20%，且全帧 p50 或
  p95 至少有一项下降 10%；未达到时记录原因，不用选择性样本宣布完成。
- 非目标阶段、GPU 时间、Draw 数、输出和错误语义不得出现无法解释的回退；关键阶段 p95 回退超过
  10% 时停止合并并归因。
- 不因增加帧槽而默认提高排队深度；如调整默认值，必须提供输入延迟或等价帧响应证据。
- Windows 与 Linux CI 保持通过；无法自动化的 Present Mode 与桌面环境差异进入带环境信息的
  性能 Record。

## 风险与未决问题

- CPU 计时本身可能改变极短阶段的分布；需要批量写入预分配缓冲并测量观测开销。
- acquire 和 present 的耗时受驱动、桌面合成器、窗口遮挡、电源状态及刷新率影响，跨机器绝对值
  不宜直接比较。
- GPU timestamp 的可用范围、周期换算和回读延迟依赖设备；现有 F-09 能力不足时先扩展内部工具，
  不立即扩大公共查询 API。
- Validation 成本可能主要位于外部 Layer；只能减少 Granit 的冗余调用，不能把关闭 Layer 当作
  引擎优化结果。
- 标题栏 FPS、外部叠加层和 benchmark 输出可能采用不同采样窗口；必须明确数据源，避免把展示
  平滑差异误判为性能没有变化。
- 若热点最终位于 ImGui 自身 Demo 构建或平台事件循环，应记录边界并停止 Granit 内部改动。
