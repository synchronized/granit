# S-77：0.42.0 Model Viewer 架构收敛

## 状态

- 文档状态：已确认
- 实现状态：进行中
- 目标版本：v0.42.0
- 后续任务：[S-78 Linux 与 Emscripten 可靠性](S-78-0.42.0-model-viewer-platform-reliability.md)

## 背景与问题

当前 Model Viewer 已把 Desktop/Web 壳层、Application、UI、Core 和 Render Runtime 拆成多个文件，
但拆分主要沿实现步骤形成，没有完全对应稳定职责：

- `examples/common/model_viewer` 同时包含可复用的 glTF→GPU 映射和 Viewer 专属材质编辑状态；
- `application_core`、`viewer_session`、`model_loading_session` 与 `scene_prepare_task` 分别保存部分
  加载生命周期；
- `render_service`、`render_runtime` 与 `render_task_executor` 形成多层转发，所有权和线程边界需要跨类
  才能理解；
- Web Shell 和 Observer 仍参与进度呈现，Application 不是唯一业务状态来源；
- `gpu_scene` 同时负责计划、上传、材质、纹理、Scene Snapshot 和更新，粒度过大。

本任务从职责重新设计 Example 私有结构，不受当前文件布局约束。最终仍保留 `model_viewer` 作为
Sample 名称，但不再用它命名可被多个示例复用的支持层。

## 非目标

- 不把 Example 私有代码安装或导出为 Granit 公共 SDK。
- 不建立通用 Scene Graph、Editor Framework 或公共 glTF Runtime。
- 不以抽象为目的增加接口；只有存在第二个调用方或明确替换关系时才进入 Common。
- 不改变 RenderPipeline、Material、Shader Library 和持久化资产格式的公共契约。
- 不为被取代的 Example 私有类、头文件和 CMake Target 保留兼容入口。

## 目标分层

```text
platform entry
  -> model_viewer_app
       -> asset_manager / task_system
       -> model_load_operation
       -> viewer_document
       -> render_dispatcher -> viewer_renderer
       -> viewer_ui
  -> gltf_rendering support -> Granit public API
```

依赖只允许自上而下。平台入口不能直接操作 GPU Scene；Common 支持层不能依赖 Model Viewer UI、
状态或浏览器测试；Viewer Document 不持有 Renderer 和平台对象。

## 核心职责

### `model_viewer_app`

顶层 Application 只推进状态机、接收输入并协调加载、渲染和 UI。它不直接解析 glTF、创建 GPU
资源或管理线程队列。Desktop/Web 只向它提供启动参数和执行策略。

### `model_load_operation`

作为加载生命周期的唯一状态来源，依次处理资产请求、CPU Scene 准备、GPU 计划、分步上传和
Pipeline 准备。它暴露不可变快照，包含阶段、进度、说明、取消能力和结构化错误。

Asset Manager 继续负责读取、依赖发现、缓存、请求合并、取消和资产级进度。加载操作只组合这些
结果，不复制 Source、Loader、缓存或依赖图。

### `viewer_document`

只保存 Viewer 业务状态：当前模型、相机、选择、灯光、材质编辑值和显示设置。它不持有 Window、
Swapchain、Renderer、任务线程或平台回调。

### `viewer_renderer`

唯一持有 Renderer、Surface、Swapchain、RenderPipeline、GPU Scene、Font 和呈现恢复状态。所有
要求 Renderer 线程亲和性的操作都集中在这里，不通过 Service/Runtime 双层重复暴露。

### `render_dispatcher`

只解决执行策略、Renderer 线程亲和性、帧队列上限、不可丢控制任务和完成回执。Desktop 注入专用
线程策略，Web 注入主线程协作策略；两端消费相同任务和状态转换。

普通 CPU 工作继续使用 `task_system`。Render Dispatcher 可以复用其 `executor` 概念，但帧替换和
GPU 顺序属于渲染策略，不塞入通用 Task System。

### `viewer_ui`

只读取加载快照和 Viewer Document，产生用户意图及 Canvas Draw Data。它不访问平台 DOM、不解析
控制台文本，也不直接执行 GPU 操作。

## 类型收敛

| 当前类型 | 目标处理 |
|---|---|
| `application_core` | 删除；纯业务状态进入 `viewer_document`，帧组装进入 `frame_builder` |
| `viewer_session` | 由 `viewer_document` 与 `model_load_operation` 取代 |
| `model_loading_session`、`scene_prepare_task` | 合并为可轮询的 `model_load_operation` |
| `render_runtime` | 收敛为唯一资源所有者 `viewer_renderer` |
| `render_service`、`render_task_executor` | 前者改为 `render_dispatcher`；后者收敛为其注入的 `render_execution_policy` |
| `pipeline_prepare` | 变成 `viewer_renderer` 的渐进准备步骤 |
| `gpu_scene` | 拆成 `scene_plan`、`scene_resources`、`scene_upload` 和 `scene_snapshot` |
| `environment_ktx2` | 改为 Asset Manager 注册的 Environment Loader |
| `material_edit` | 共享更新值改为 `material_update`；Viewer 专属编辑状态进入 `viewer_settings` |

## 加载与执行契约

统一阶段如下：

```text
bootstrap
  -> presentation_ready
  -> asset_fetch
  -> scene_prepare
  -> gpu_upload
  -> pipeline_prepare
  -> viewer_ready
```

每个 Tick 只推进有限工作，然后返回主循环绘制 UI。CPU 解析可以在 Worker Executor 运行；GPU 创建
通过 Render Dispatcher 进入正确线程。不得从资源进度回调重入完整渲染。无法分步的短操作须记录
耗时上限，超过单帧预算的操作必须拆分。

## CMake Target 边界

- `granit_example_gltf_support`：CPU glTF 数据和 Asset Loader；
- `granit_example_gltf_rendering`：glTF Scene 到 Granit GPU/RenderPipeline 的私有适配；
- `granit_sample_model_viewer_core`：Document、加载操作、Renderer、Dispatcher 和 UI；
- Desktop/Web 只生成很薄的最终可执行目标；
- 浏览器测试钩子和 Pipeline Validation 使用独立测试目标，不链接进正式 Sample。

Target 名称表达真实职责，不继续保留 `support`、`service`、`runtime` 等含义重叠的别名。

## 实施顺序

1. 建立目标目录和依赖门禁，把共享 glTF 渲染代码及其测试迁出 `common/model_viewer`。**已完成。**
2. 拆分 `gpu_scene`，保持现有 CPU 计划和 GPU 行为测试持续通过。**已完成。** 计划、上传、
   Snapshot 和资源所有权现分别位于 `scene_plan`、`scene_upload`、`scene_snapshot` 与
   `scene_resources`。
3. 引入 `viewer_document` 和 `model_load_operation`，删除重叠 Session/Core/Prepare 状态。
   **已完成。** `model_load_operation` 独占资产请求和异步 CPU 准备生命周期，`viewer_document`
   独占 CPU Scene、查看状态、相机与性能历史；`application_core`、`viewer_session` 和
   `scene_prepare_task` 均已删除，Application 直接协调这两个边界。
4. 建立 `viewer_renderer + render_dispatcher`，迁移资源所有权和线程执行契约。
   **已完成。** `viewer_renderer` 独占 Renderer、呈现对象、Pipeline、GPU Scene、环境贴图和
   Canvas 资源；帧包只传递业务值，由渲染线程创建 Scene Snapshot。`render_dispatcher` 注入
   inline/threaded 执行策略，Renderer 不再反向引用 `viewer_session`；Pipeline 预热、材质更新、
   调试显示和纹理绑定查询也统一经过 Dispatcher。Renderer 创建、事件推进、加载帧和资源统计均在
   同一执行策略中运行。
5. 让 `model_viewer_app` 只协调状态转换，并让 Desktop/Web 使用同一个 Application 主体。
   **已完成。** `viewer_application` 直接协调 Document、加载操作、Dispatcher 和 UI；Desktop 与
   Web 入口只提供平台描述和 Observer，共用同一 Application 状态机。
6. 整理 UI、测试钩子、CMake Target 和命名，删除旧文件与转发层。
7. 由 S-78 完成跨平台加载 UI、生命周期和远端验收。

每一步完成相关测试后创建聚焦提交。迁移期间允许短暂增加新旧内部路径，但阶段提交不得同时保留
两套可选择实现。

## 测试与验收

- 依赖检查证明 Common 不引用 Model Viewer，平台壳不绕过 Application 访问渲染资源。
- Asset Manager 继续覆盖请求合并、依赖、缓存、取消、失败和进度。
- glTF Rendering 覆盖计划溢出、材质/纹理、上传回滚、Scene Snapshot 和资源销毁。
- 加载操作覆盖合法阶段、进度单调、未知总量、取消竞态、失败和重复完成。
- Render Dispatcher 覆盖 inline/threaded 策略、帧替换、控制任务、Flush、停止和完成回执。
- Viewer Renderer 覆盖初始化、上传、Pipeline、帧、Resize、Surface 恢复和 Shutdown。
- 被取代类型、头文件、Target 和兼容别名全部删除。

## 风险与约束

- 这是 Example 私有重构，不能顺势扩大公共 ABI。
- `gpu_scene` 拆分涉及资源所有权，阶段提交必须保持失败回滚和销毁次序可测。
- Desktop/Web 执行策略不同，但不得通过平台宏形成两套业务状态机。
- 文件变多不是目标；只有职责、所有权或依赖边界不同才拆文件。
