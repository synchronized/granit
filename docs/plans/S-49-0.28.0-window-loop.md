# S-49：0.28.0 Window 跨平台可选主循环

## 状态

**实施中，P1。** 本任务为 S-48 线性教程提供 Win32、XCB、Wayland 与 Emscripten 共用的逐帧入口，
同时保留引擎和外部框架自行管理事件循环的能力。

## 背景与目标

Window System 已统一窗口、输入、状态查询和 Surface 创建，但应用仍需分别编写桌面阻塞循环与
Emscripten 浏览器回调。两套壳层容易让 Resize、停止、异步 Renderer 初始化和资源清理发生漂移。

本任务在 Window component 中增加可选 Loop。它只负责推进 Window 事件并按平台调度宿主 Tick；
Renderer、Surface、Swapchain、资产和应用状态仍由宿主管理。Tutorial 可以复用相同 Tick，复杂引擎
仍可直接调用 `granit_window_system_process_events`。

## 非目标

- 不让 Window component 依赖 Renderer、RenderPipeline、SDL、ImGui 或资产系统。
- 不接管任务系统、固定更新、渲染线程、后台线程或资源加载。
- 不删除或弱化现有非阻塞事件泵和事件轮询接口。
- 不允许异常、STL 对象或宿主分配器跨越 C ABI。
- 不让 Granit DLL 删除宿主通过 `user_data` 提供的对象。

## 已确认决策

### 公共模型

C ABI 使用定宽 Action、Tick 回调、Shutdown 回调和可扩展描述结构：

```c
typedef uint32_t granit_window_loop_action;

#define GRANIT_WINDOW_LOOP_CONTINUE UINT32_C(0)
#define GRANIT_WINDOW_LOOP_IDLE UINT32_C(1)
#define GRANIT_WINDOW_LOOP_STOP UINT32_C(2)

typedef granit_result (*granit_window_loop_tick_fn)(
    void* user_data,
    granit_window_loop_action* action);

typedef void (*granit_window_loop_shutdown_fn)(
    void* user_data,
    granit_result reason);
```

`granit_window_system_run_loop` 为可选托管入口。每轮先调用现有
`granit_window_system_process_events`，再调用宿主 Tick。Tick 返回错误或 Stop 时结束，并且恰好调用
一次 Shutdown。`user_data` 始终由宿主拥有，必须持续有效到 Shutdown 返回。

同一 Window System 同时只能运行一个 Loop。Loop、事件处理和回调均在 Window System 创建线程执行；
回调不得递归调用托管 Loop。宿主可以继续在 Tick 中轮询窗口和输入事件。

### 平台语义

- Win32、XCB 和 Wayland 在调用线程运行阻塞循环；Continue 立即进入下一轮，Idle 使用短暂平台无关
  等待，避免最小化或异步等待时忙循环。
- Emscripten 使用 `emscripten_set_main_loop_arg`，由浏览器逐帧调用同一 Tick。注册成功后控制权交给
  浏览器，不能依赖 `run_loop` 之后的普通栈清理。
- Stop、Tick 错误或显式停止都会取消浏览器循环并调用 Shutdown；浏览器页面导航仍由宿主管理。

### ABI 与所有权

- DLL 只保存回调函数指针和不透明 `user_data`，不复制或释放宿主对象。
- 回调不得抛出异常穿过 ABI。C++ trampoline 为 `noexcept`，失败转换为 `granit::result`。
- Shutdown 在宿主模块中执行，宿主可在其中释放自己的对象；Granit 内部状态由 Window component
  自己释放。
- 普通回调在创建线程同步执行，不从隐藏线程调用。
- 若回调来自可卸载插件，插件必须等到 Shutdown 完成后才能卸载。

### C++ 包装

增加 `window_loop_action`、`window_loop_desc` 和 `window_system::run_loop`。第一版保持显式函数指针和
`void*`，避免模板包装隐式转移宿主对象所有权。Tutorial 使用静态或其他明确长生命周期的应用状态，
后续有第二个 Consumer 需求时再评审拥有型模板适配器。

## 实施顺序

1. **S-49A 契约与平台无关状态机**：增加 C/C++ 头、参数校验、单 Loop 与线程约束、回调停止和
   Shutdown 一次性语义，并补充无窗口单元测试。
2. **S-49B 桌面调度**：让 Win32、XCB 与 Wayland 使用同一托管循环，覆盖 Continue、Idle、Stop、
   Tick 错误和事件泵错误。
3. **S-49C Emscripten 调度**：接入浏览器主循环，覆盖异步开始、停止、错误与 Shutdown 生命周期，
   Browser Smoke 验证持续推进。
4. **S-49D Tutorial 迁移**：把 Tutorial 1 拆成共享应用 Tick，由 Window Loop 同时驱动桌面和浏览器；
   Renderer Ready 之前只推进事件，不创建 Surface 和 GPU 资源。
5. **S-49E 文档与矩阵**：更新 Window Reference、Tutorial、安装头与 Consumer，运行 Windows、Linux、
   Emscripten、shared/static 和文档检查。

## 测试与验收

- C11 头和 C++20 聚合头可独立包含，新结构布局进入 ABI 检查。
- 参数为空、结构过小、未知 Action、重复运行、错误线程和递归运行返回确定结果。
- Continue 保持推进；Idle 不忙循环；Stop 和 Tick 错误均只调用一次 Shutdown。
- Shutdown 中可以安全释放宿主状态，Window DLL 不调用宿主对象的分配器。
- 桌面 Tutorial Smoke 渲染、重建并自动退出；浏览器 Tutorial Smoke 至少推进三帧和一次 Resize。
- 手动事件循环及已有 Window、Input、SDL3 和浏览器示例行为保持不变。

## 风险与未决问题

- Emscripten 的托管入口具有浏览器控制流语义，文档必须禁止依赖调用后的局部对象析构。
- Idle 首版采用短暂等待；只有实际功耗或延迟数据证明需要时，才增加 Win32/XCB/Wayland 原生等待。
- 拥有型 C++ Application 模板涉及宿主对象销毁和异步注册失败所有权，第一版不公开。
- 若未来需要多个独立 Loop 或跨线程停止，应新增显式 Loop 句柄，而不是扩大 Window System 隐式状态。
