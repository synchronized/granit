# S-75：0.40.0 Deferred 与多 Pass 渲染

## 状态

**已完成并随 v0.40.0 发布，P1。** 本任务新增 `07_deferred`，以可运行教程验证 MRT、G-buffer、
中间纹理采样、多 Pass 依赖和尺寸相关资源生命周期。

## 背景与目标

Granit 已在 Vulkan 与 WebGPU 公开 MRT、Texture View、Sampler、Graphics Pipeline 和显式命令录制，
但现有 Tutorial 仍以单颜色附件或全屏程序化效果为主，没有把这些能力组合成完整多 Pass 工作流。

本任务使用 Deferred Rendering 作为能力探针：Geometry Pass 把场景属性写入三张 G-buffer，Lighting
Pass 通过全屏三角形读取这些纹理并计算多个点光源。它既能展示一个新的渲染特性，也能检查现有 API
是否足以清晰表达附件创建、Pass 切换、资源绑定、Resize 和调试观察。

## 非目标

- 不以教程为理由直接增加公共 Render Graph 或另一套资源状态系统；
- 不实现完整 Deferred PBR、透明物体、Shadow、IBL、SSAO、Tiled 或 Clustered Lighting；
- 不引入 Bindless、Async Compute、多 Queue 或后端专有路径；
- 不改写公共 RenderPipeline 的 Forward PBR 实现；
- 不把教程局部资源管理代码提升为公共 SDK。

## 已确认设计

### 渲染流程

```text
Instanced Cubes
      ↓ Geometry Pass（3 个颜色附件 + Depth）
Position/Depth + Normal + Albedo/Material
      ↓ Lighting Pass（全屏三角形）
Backbuffer
      ↓ Canvas / ImGui
Present
```

Geometry Pass 使用带颜色变化的实例化 Cube 场景和 Orbit Camera，形成足够稳定的深度、法线和材质
差异。Lighting Pass 在 Fragment Shader 中循环固定上限数组内的活动点光源；首版支持 1～64 个光源，
运行时只修改活动数量和参数，不为每个光源提交一次 Draw。

### G-buffer 契约

| 附件 | 建议格式 | 内容 |
|---|---|---|
| Position/Depth | `rgba16_float` | View-space Position.xyz 与 Linear Depth |
| Normal | `rgba16_float` | View-space Normal.xyz 与保留通道 |
| Albedo/Material | `rgba8_unorm` | Albedo.rgb 与材质参数 |
| Depth | `d32_float` | Geometry Pass 深度测试，不在 Lighting Pass 直接采样 |

初始化时检查颜色附件数量、格式渲染和采样能力。后端无法满足共同基线时返回明确的不支持结果，不用
后端私有格式改变教程语义。G-buffer Texture 和 View 由 Tutorial 持有，其生命周期覆盖对应窗口尺寸
下的所有帧。

### Pass 与资源生命周期

每帧使用同一个 Frame Recording 顺序录制 Geometry、Lighting 和 Canvas。Geometry Pass 结束后，
Lighting Pass 将三张颜色附件作为采样纹理读取；资源状态和后端同步继续由现有 Recorder 契约处理，
教程不传递 Vulkan Barrier 或 WebGPU Pass 对象。

窗口尺寸变化时，先等待 Frame Context 允许的安全重建点，再按新尺寸重建 G-buffer Texture、View 和
相关 Bind Group。零尺寸期间跳过绘制但继续处理事件；恢复后只重建尺寸相关资源。失败不得留下新旧
尺寸资源混用的半初始化状态。

本版本使用持久的尺寸相关 Texture，不增加帧级 Transient Texture。若实现中出现跨多个教程重复且
无法由局部 RAII 消除的生命周期问题，记录具体证据并另立公共能力计划，不自动扩大 S-75。

### 交互与调试

教程复用统一 Granit ImGui 主题、性能面板和 Orbit Camera，并提供：

- Final Lighting、Position/Depth、Normal、Albedo 四种输出模式；
- Point Light 数量、动画开关、动画速度和 Exposure；
- Geometry 与 Lighting Pass 的 GPU 时间（能力可用时）；
- 当前 G-buffer 尺寸、格式和活动光源数量。

Smoke 模式固定相机、光源、时间和输出模式。调试视图复用 Lighting Pass 的全屏路径，通过 Uniform
选择输出，不增加独立平台代码。

### 跨平台与 Shader

Desktop Vulkan 和浏览器 WebGPU 编译同一个 `main.cpp` 主体。平台壳只负责既有入口参数和主循环
接入；资产加载、状态机、渲染和 UI 不分叉。Geometry 与 Lighting 的 Vertex/Fragment 入口位于同一
HLSL-first Shader Library，并由现有工具链生成 SPIR-V 与 WGSL 变体。

## 测试与验收

- Vulkan 与 WebGPU 都能创建三颜色附件加 Depth 的 Geometry Pipeline；
- 三张 G-buffer 输出具有确定的非零摘要，附件顺序或格式不匹配时得到明确错误；
- Lighting Pass 读取当前帧 G-buffer，Final 与三种调试模式产生可区分结果；
- Light Count 变化只更新参数，不改变 Draw 数量或重建 Pipeline；
- Geometry、Lighting 与 Canvas 顺序通过 Vulkan/WebGPU Validation；
- Resize、最小化和恢复不使用旧 View，不泄漏资源，也不提交零尺寸 Pass；
- Desktop 与 Web 使用同一业务实现，浏览器测试能查询 Pass 数量、活动光源和输出模式；
- 文档检查、`git diff --check`、Windows/Linux、Emscripten 和安装 SDK 验收通过。

## 风险与未决问题

- `rgba16_float` G-buffer 带宽较高，但能减少首个能力教程中的编码噪声；后续可单独比较压缩布局。
- 浏览器软件实现的多光源 Fragment 循环可能较慢，默认光源数量以 CI 和普通设备稳定运行为准。
- 显式 API 可能暴露重复的附件重建样板；只有多个真实调用方出现相同问题后，才评估
  Transient Texture 或 Render Graph。
- 本任务验证的是多 Pass 资源表达能力，不把教程画质作为替代现有 Forward PBR 的依据。
