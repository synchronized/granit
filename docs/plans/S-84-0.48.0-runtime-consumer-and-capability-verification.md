# S-84：0.48.0 Runtime Consumer 与图形能力验证

## 状态

**实施中。** S-84A 部署指南和 S-84B Runtime Bundle 归档布局测试已完成；本计划承接已发布的
v0.47.0，目标是把 Vulkan Runtime Bundle 从“可发布”推进到“应用可以独立接入并可诊断”，同时
参考 bgfx 的单项示例方式验证 Granit 当前已有图形能力。

## 背景与目标

v0.47.0 已交付 Windows/Linux Runtime Bundle、Loader 自动回退、Validation Layer 配置和公开下载
校验，但还需要一个不依赖 Granit 源码树或开发机全局 Vulkan SDK 的真实 Consumer 闭环。现有
`09_particles`、`10_transparency`、`11_capabilities` 已作为能力探针存在，需要完成跨平台验收并把
真实缺口与明确不支持项记录下来。

本版本回答三个问题：

1. 下载 Runtime Bundle 后，普通应用能否按文档完成部署、启动和失败诊断；
2. Loader、Validation Layer 和驱动/ICD 缺失时，错误边界是否清晰且不会误报 Vulkan 可用；
3. Granit 已有跨后端能力是否有可运行、可回归的 Tutorial 证据，哪些需求应留给 Gneiss。

## 非目标

- 不分发或安装 NVIDIA、AMD、Intel 等厂商驱动和 ICD；
- 不把 Vulkan SDK、Headers 或 Validation Layer 传播为普通 SDK 的传递依赖；
- 不在本版本实现 SVT/虚拟纹理、纹理预算、驻留和回收，这些属于 Gneiss 资源系统；
- 不因为能力探针结果直接新增 OIT、GPU-driven 多批次、Bindless 或专用 Particle 公共 API；
- 不新增 Vulkan 类型、句柄或原生 Vulkan 公共接口；
- 不扩展 macOS MoltenVK Runtime Bundle；
- 不把示例的临时状态和调度器下沉到 Granit 公共运行时。

## 已确认决策

### 1. Runtime Bundle 继续保持独立分发

公开 Runtime Bundle 仍按平台和架构下载，应用目录负责部署：

```text
Windows: 应用 exe 同目录/vulkan-1.dll
Linux:   可执行文件目录的 ../lib/libvulkan.so.1
```

Granit 默认使用 `system -> bundled` 的 `auto` 顺序。应用可以通过
`GRANIT_VULKAN_RUNTIME`、`GRANIT_VULKAN_LOADER_PATH`、`GRANIT_VULKAN_VALIDATION` 和
`GRANIT_VULKAN_VALIDATION_PATH` 进行诊断或开发期配置；不新增公共 ABI。

### 2. Consumer 验证优先于新增功能

先建立最小安装 SDK Consumer 和 Runtime Bundle 部署测试，再决定真实缺口是否值得进入公共 API。
Consumer 不包含 Vulkan 头文件，不引用 `src/` 私有头，也不依赖源码树中的 Loader 或 Validation
Layer。

### 3. Tutorial 是能力证据，不是功能需求生成器

继续使用 `09_particles`、`10_transparency` 和 `11_capabilities` 作为小而确定的探针。探针只记录
当前能力、跨后端差异、包装摩擦和明确不支持项；只有跨后端语义稳定、所有权清晰且有独立复现时，
才创建后续公共 API 计划。

## 实施顺序

1. **S-84A 文档与部署契约**：补充 Runtime Bundle Guide，固定 Windows/Linux 目录布局、下载、
   SHA-256 校验、Loader 选择、Validation Layer 配置和常见失败诊断。
2. **S-84B 最小 Consumer**：新增只依赖安装 SDK 的 C11/C++20 Consumer，验证共享库、Runtime
   Bundle 和应用启动路径；必要的部署辅助保持在 CMake/测试层，不进入公共 ABI。
3. **S-84C 干净环境验证**：在 Windows/Linux CI 分别覆盖 system、bundled、auto、显式 Loader
   路径、Validation `off/auto/on`，并区分 Loader 缺失、Validation 缺失、驱动/ICD 缺失。
4. **S-84D Tutorial 能力矩阵收口**：完成 `09_particles`、`10_transparency`、`11_capabilities`
   的 Vulkan/WebGPU Smoke、固定参数、Resize、失败清理和浏览器验证，更新能力矩阵事实。
5. **S-84E Gneiss 边界审计**：对 `UPSTREAM-044` 后续需求逐项判断是 Granit 通用 GPU 能力、
   Gneiss 资源驻留职责，还是明确不支持；不把 SVT、预算和回收逻辑移入 Granit。
6. **S-84F 发布验收**：完成文档检查、安装 Consumer、共享/静态构建、Windows/Linux、Emscripten
   回归和公开制品下载复验后发布 v0.48.0。

## 测试与验收

- 安装后的 C11/C++20 Consumer 不引用源码树、Vulkan SDK 头文件或全局开发机路径；
- Windows/Linux 应用在系统 Loader 不可用时能按 `auto` 使用 Bundle，且 Loader 和 ICD 都缺失时返回
  明确错误，不崩溃、不误报；
- Validation `off/auto/on` 行为、路径配置和缺失诊断均有自动测试；
- Runtime Bundle 的文件布局、manifest、许可证和 SHA-256 与公开 Release 一致；
- `09_particles`、`10_transparency`、`11_capabilities` 在 Vulkan/WebGPU 通过固定参数 Smoke，
  覆盖 Resize、最小化恢复、失败清理和浏览器验证；
- 能力矩阵明确标注已有能力、包装摩擦、真实缺口和暂不支持项；
- 不新增公共 ABI，公共头文件仍不包含 Vulkan SDK 头文件；
- Release 发布前手动确认 Windows/Linux SDK、Runtime Bundle、`SHA256SUMS` 和公开下载校验。

## 风险与未决问题

- 不同 Linux 发行版的 Loader、ICD JSON 和驱动搜索路径可能导致 Bundle 验证结果不同，需要固定
  CI 镜像和支持边界；
- 系统 Loader 已被进程加载后不能安全切换到 Bundle，因此选择必须发生在 Vulkan 初始化早期；
- Validation Layer 与驱动版本不匹配时，应保留结构化诊断，不将其误判成 Granit Loader 故障；
- 如果能力探针暴露出跨后端公共缺口，必须先建立独立设计和证据，不能在本版本中顺手扩大范围；
- Gneiss 的纹理驻留需求只有在确认 Granit 缺少通用资源生命周期能力后，才进入后续 Granit 计划。
