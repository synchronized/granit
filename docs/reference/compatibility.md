# 版本与兼容策略

## 当前承诺

Granit 当前版本为 0.x，公共 API、C ABI、C++ 包装、CMake component 和材质包仍可能发生破坏性
调整。升级 0.x 版本前必须阅读变更记录并重新编译使用者；项目目前不承诺旧二进制可以直接加载
新动态库。

“已有 ABI 回归测试”只表示仓库能够检测导出符号、结构布局和常量变化，不等于这些内容已经冻结。
发生有意的 0.x 破坏性变更时，必须同步更新测试基线、迁移说明和版本号，不能静默漂移。
Core 当前使用独立的 0.6.0 快照；Window 新增接口使用 0.5.0 增量符号快照，RenderPipeline 与
Input 继续使用 0.1.0 快照。历史快照保持不可变，新版本通过新目录记录增量或完整基线。

## 接口等级

| 接口 | 0.x 阶段 | 首个稳定版本目标 |
|---|---|---|
| 核心 `.h` C API | 可检测但未冻结 | 同一主版本内保持 ABI 兼容 |
| 可选 component `.h` C API | 可检测但未冻结 | 按 component 明确宣布后保持 ABI 兼容 |
| `.hpp` C++20 包装 | 源码接口未冻结 | 同一主版本内优先保持源码兼容，不承诺 C++ 二进制 ABI |
| CMake 目标与 component 名 | 变更必须记录 | 同一主版本内保持已发布名称和依赖语义 |
| 材质包及其他持久化格式 | 由格式版本和校验独立管理 | 只按对应格式文档声明兼容范围 |
| Vulkan 原生互操作 | 尚未公开 | 始终作为显式不稳定的高级接口，不污染基础 API |
| `src/` 内部接口和 benchmark 测量入口 | 无兼容承诺 | 不进入公共兼容范围 |

所有 component 使用统一的 Granit 包版本，但“核心稳定”不自动表示尚未宣布稳定的可选 component
同时冻结。稳定等级必须在发布说明和对应参考文档中明确标注。

## 版本规则

版本采用 `主版本.次版本.修订版本`：

- 0.x 阶段的次版本可以包含有记录的破坏性变更，修订版本只用于兼容修复。
- 首个稳定版本发布后，同一主版本内只允许兼容扩展和缺陷修复。
- 追加结构尾部字段必须保留旧 `*_VERSION_N_SIZE`，旧调用方继续按其 `struct_size` 工作。
- 新函数、枚举值和标志位只能使用新名称或此前保留的数值，不重解释已发布值。
- 删除或改变已稳定接口语义需要提升主版本，并提供迁移说明。

头文件版本宏与运行时 `granit_version_*` 返回库版本。它们用于诊断和包选择，不替代结构大小、
能力查询或具体格式版本；应用不得只按版本号猜测后端能力。

## 破坏性变更流程

0.x 阶段确需破坏性修改时，提交必须同时包含：

1. 受影响的 C API、C++ 包装、CMake component 或持久化格式范围。
2. 旧行为与新行为，以及使用者需要执行的迁移步骤。
3. 导出符号、布局、Consumer、共享/静态和相关行为测试的同步变更。
4. 版本号与变更记录更新；不能只修改基线来隐藏差异。

## 进入稳定版本的门槛

首个稳定兼容承诺至少要求：

- S-01E 保存带平台、架构、编译器和 Granit 版本身份的正式 C ABI 快照。
- Windows/Linux 的共享库、静态库、C11、C++20 和安装 Consumer 矩阵持续通过。
- 公共结构的扩展方式、所有权、线程安全、错误语义和 component 依赖均有参考文档。
- 发布流程能比较当前 ABI 与上一个稳定版本，并区分兼容扩展和破坏性变化。
- 发布说明列出稳定 component、实验性接口、已知限制和升级路径。

在这些门槛全部通过并明确发布稳定版本之前，README 的 0.x 警告继续有效。
